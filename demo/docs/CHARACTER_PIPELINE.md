# 角色生产流程

## 这份文档是什么

**给要往这个项目里加一个新角色的人。**讲流程、约束、和这些约束的来由。

和 `README.md` 的分工：

| | 讲什么 | 给谁看 |
|---|---|---|
| `README.md` 的「资产一致性实验室」 | **Gus 现在是什么样** —— 现状、命令、门禁键名 | 来读这个项目的人 |
| 本文档 | **要加一个角色该怎么做** —— 流程、规格、决策依据 | 要动手的人 |

适用范围：等距投影、24×48 网格、锁定调色板的像素角色。

> **写作约定**：本文档**不写代码里的当前阈值**，只写键名并指向源文件。阈值会变，写进文档就会腐化——这个项目已经吃过一次亏（见下文「文档必须机械地为真」）。
> 反过来，**历史缺陷的数字可以放心写**：它们是既成事实，不会改变，而且它们是每条门禁存在的唯一理由。

## 一、核心原则

> **像素可以是画的，语义必须是声明的。**

这条原则不是审美偏好，是从「哪些门禁能只看图验出来」推出来的：

| 门禁 | 只看图能验吗 | 为什么 |
|---|---|---|
| 每帧至少一只脚落在它自己的地面行 | ✅ 能 | 纯像素属性 |
| 承重脚每帧后移量 = 角色每帧前进量 | ❌ 不能 | 需要知道**这一帧哪只脚是支撑脚** |
| 髋高 = 该帧的 body 位移 | ❌ 不能 | 需要知道**髋在哪一行** |
| 躯干亮面与近手臂同侧 | ❌ 不能 | 需要知道**哪条是近臂** |
| 扣除整体位移后的四肢动作量 | ❌ 不能 | 需要能把四肢从整体里分离 |

从像素里猜「这两坨深色哪个是支撑脚」是不可靠的。**一旦交付物是「一张做好的精灵表」，语义就丢了**，门禁只能退化成静态的、可从单帧猜出来的属性——而那正是这个项目之前的状态，也正是它漏掉整整一类缺陷的原因。

## 二、分层责任

| 层 | 谁负责 | 交付物 |
|---|---|---|
| **身份层** head + torso | 设计师 / 生成模型 | 4 个方向 × 1 张中立站姿 |
| **运动层** 四肢 | 管线程序化生成 | 姿态表（数学，不是画） |

这条缝**不是新发明的**——`rig.json` 里的 `identityLocked: ["head", "torso"]` 架构里本来就有。

**为什么这么切：**

- 24×48 下四肢只有 3-5px 宽。`character_motion.py` 的 `_limb_rows` 做逐扫描线光栅化，保证肢体在每一行宽度均匀——这是 3px 宽的腿能在原生尺寸下读出来的原因。手画反而稳不住。
- head + torso 约占可见剪影的一大半，形象全在这儿。这也正是当前**最弱**的部分：程序化画出来的躯干四个方向几乎相同，而 `assets/gus-rig/reference/gus-turnaround-v2.png` 那张参考图有真正的身体比例和正背区分。这个差距是真实的，也正是设计师该补的位置。

## 四、角色规格：解剖决定步态

**这是本次最贵的一课。**当初计划里写了 14px 步幅，动手才发现几何上做不出来——需要 19px 腿长，是实际的 2.1 倍。

步幅不是可以自由选的设计参数，它被解剖结构锁死：

```
腿长      = 地面行 − 髋高
最大步幅  = 2 × 腿长 × sin(摆幅角)
每帧位移  = 步幅 ÷ 每步帧数          ← 必须是整数像素
帧长      = 步幅 ÷ 移动速度 ÷ 每步帧数 ← 需落在可读区间（约 50–140ms）
```

Gus 的实测：髋在 y=36、地面在 y=45，**腿长仅 9px**，占身高 25%（人类约 48%）。这直接决定了它只能小碎步。

> **摆幅角必须显式声明并校验。**Gus 实际发布的 8px 步幅隐含 ±26.4° 摆幅——比常规的 ±20-22° 激进，站得住，但当时没算，是碰巧。这类「碰巧」正是流程要消灭的东西。

**规格清单**（新角色开工前必须先定，全部落在 `rig.json` 与编译器常量里）：

| 组 | 内容 |
|---|---|
| 身份 | slot id、画布尺寸、anchor、调色板（**必须是世界调色板的子集**） |
| 解剖 | 髋高、肩高、踝高、髋横距、肩横距、地面行 |
| 比例 | 头高/宽区间、总高区间、头身比上限 |
| 步态 | **摆幅角** → 推导出步幅 / 每帧位移 / 每步帧数 / 帧长（不手填） |
| 动作 | idle / walk / work 各几帧 → 派生列序、总帧数、图集布局、帧 id |
| 朝向 | 引用共享的等距近侧轴，**不要自己定义** |
| 门禁 | 五类阈值 |

> **朝向轴是等距投影的属性，不是角色的属性**，所以它不在这份清单里——直接从 `codex_v0/isometric.py` 取。那里的 `FORWARD_SCREEN_X` 和 `NEAR_SIDE_SCREEN_X` 是**从投影公式推导出来的**，不是手写常量，导入时有断言校验。不要在角色模块里另写一份。

## 五、设计师交付规格

> 本节可以单独摘出来发给外部设计师，不含内部实现细节。

### 交付什么

**4 张图**：`southeast` / `southwest` / `northwest` / `northeast` 四个方向，每个方向 **1 张中立站姿**。

**不是**精灵表。不要画走路帧、不要画动作序列——四肢由管线生成。

### 硬约束

| 项 | 要求 |
|---|---|
| 画布 / anchor | 按项目给定值（见 `rig.json` 的 `frame`） |
| 调色板 | 必须是项目世界调色板的子集，见 `assets/core-pack.spec.json` 的 `palette` |
| 透明度 | **二值**——只能全透明或全不透明，不允许半透明像素 |
| 比例 | 头高/宽、总高必须落在给定区间（见 `READABILITY_CONSTRAINTS`） |
| 正面（south 两向） | 要有脸：五官可辨，皮肤占比不低于下限 |
| 背面（north 两向） | **真背面**：完全看不到脸，只有后脑勺和后颈 |
| 正 vs 背 | 躯干必须有**实质差异**，不能只差一块领带 |

### 我们会自动做

- 调色板量化、网格对齐、尺寸归一
- 四肢的全部姿态与帧
- 五类门禁检查、QA 证据生成

### 你必须保证

- **形象一致性**：四个方向是同一个人
- **正背区分**：走远时读得出他在走开，而不是面朝你倒退
- **剪影可读**：在 1× 原生尺寸下（不是放大后）能看清

### 为什么背面这么强调

Gus 上一版的 northeast 方向有 **18.9% 的皮肤像素**——一张正对镜头的脸。而躯干正面和背面**只差 6 个像素**（就是一块领带矩形）。于是走 northeast 时，腿往右上方迈步（远离镜头），头和躯干却仍面朝观众。大脑把它读成「正面朝你却在倒退」。

## 七、五类门禁

门禁的作用是**在缺陷进入游戏之前拦住它**。每一类都对应一个真实发生过、并且一路通过了当时全部检查的缺陷。

| 层 | 回答什么问题 | 防的是哪个真实缺陷 |
|---|---|---|
| **可复现** | 能否逐字节重建？ | ——（这一层一直很好） |
| **契约** | 是否符合管线形状？ | 帧数曾在 7 处互不派生地硬编码，帧索引表有 3 份副本 |
| **可读性** | 玩家在原生尺寸下看得见吗？ | 腿与躯干共用同一组颜色，整个腿部区域只有 **2 个**对比像素 |
| **运动学** | 动作是否符合物理？ | 走路一半时间**双脚腾空 2px**；支撑脚每步**滑 5-6px**；work 全动作只动 **4px** |
| **朝向语义** | 人物是否朝着他走的方向？ | 北向露脸 **18.9%**；躯干正背只差 **6px**；近侧在 SE/SW 上**反向** |
| **运行时** | 播放时是否仍然成立？ | 步频与移动速度解耦，**56% 滑步** |

具体阈值键名见 `codex_v0/character_motion.py` 的 `READABILITY_CONSTRAINTS`；实施位置在 `_validate_motion` 和 `_validate_compiled_frames`。

### 三条设计教训

**1. `verified: true` 回答的是「能不能重建」，不是「能不能用」。**

这套管线的确定性做得非常好——哈希、收据、逐像素比对、两次构建字节一致。但它把**可复现性**当成了**质量**。上一版 12 条门禁**全部是单帧静态属性，零条测运动**；唯一与动画有关的判据是「相邻帧不能完全一样」。一个双脚腾空、脚底打滑、work 只动 4 个像素的角色，可以完美通过每一次验证。

**2. 门禁必须针对语义，不能针对像素差异总量。**

「四个方向的剪影必须差 ≥N 像素」这种门禁抓不住朝向问题——四个各自独立手绘的头天然差 175-245px，无论它们是否真的在转向都能过关。而且这条门禁在物理上就是错的：一个人站着的正面和背面轮廓本来就几乎一样。

正确做法是直接度量语义：北向头部皮肤占比、正/背躯干差异、躯干亮面与近臂是否同侧。

**3. 多轴对称必须显式枚举，光看渲染图看不出来。**

这个模块里同时存在三条方向轴：

| 轴 | 分组 | 用途 |
|---|---|---|
| A 屏幕 x 前进轴 | `{SE,NE}` vs `{SW,NW}` | `forward` |
| B 南北向背轴 | `{SE,SW}` vs `{NW,NE}` | 领带、正/背面 |
| C 等距近侧轴 | `{SE,NW}` vs `{SW,NE}` | 近肢体、躯干亮面 |

近侧曾经从 A 派生，而躯干翻领用 C，**在 SE/SW 上永远相反**，人物被拧着。这个 bug 在渲染图上只表现为「有点别扭」，反复看都没定位到；把每个方向分支列表、按轴分类之后一眼就出来了。

**同类事故这个项目发生过两次。**`core-v1` 第一批墙体 PNG 的 NW/NE 方向与 footprint 轴相反，当时的处理是在 `web/scene.mjs` 加了一张永久的运行时交换表 `CORE_V1_LEGACY_RENDER_ASSETS` 外加 `geometryVersion` 开关，**没有在源头修**——那张补偿表至今还在代码里。

**可执行的做法**：把每条轴定义成命名常量（`NEAR_SIDE_SCREEN_X` 就是这么做的），所有消费者从它取值，再加跨层一致性断言。这类断言廉价且致命有效。

## 八、验收清单

按缺陷类别组织，不按文件。每一条都对应一个真实发生过的缺陷。

- [ ] **可复现** —— 连续两次 build，`pngSha256` 一致
- [ ] **契约** —— 帧数 / 列序 / id 序列 / 图集偏移全部由规格派生，源码里没有字面量
- [ ] **可读性** —— 头身比、ink 占比、肢体外露、腿间负空间、腿部对比像素全部达标
- [ ] **运动学** —— 每帧都有支撑脚；承重脚每帧位移 = 角色每帧位移；扣除整体位移后的四肢动作量达标
- [ ] **朝向** —— 背面不露脸、正面不丢脸、正/背躯干差异达标、**跨层近侧一致**
- [ ] **运行时** —— 步频由实际位移驱动；转向不重置相位；降级矢量渲染器与正式渲染器同相
- [ ] **provenance** —— 文档描述的流程与代码实际行为一致（见下节）
- [ ] **实机** —— 走直线看脚有没有打滑；走折线看拐弯有没有跳回起始姿势；走北向看是不是真的在走开

## 九、逃生口：authored 模式

非人形角色、披风、特殊技能动作——这些场景下四肢不该由姿态表生成。规则是：

**允许交付像素，但必须随像素交付姿态元数据。**每一帧声明：支撑脚是哪条腿、髋在哪一行、近侧在哪一边。

门禁照常跑。这本身就变成一条很强的检查：你声明支撑脚在某一行，编译器就去看那只脚的最低行是不是真的在那里。**声明与像素不符 → 直接失败。**

这比「从图里猜」可靠得多，也比「完全不查」安全得多。

## 十、加一个新角色实际要动哪些地方

> ⚠️ **今天加第二个角色不是复制粘贴，是一次约 6-8 人天的泛化工程**（另加像素美术时间）。
>
> 原因不是编译器写得差——它绝大部分是通用机器，Gus 专属的手绘美术（`HEAD_PIXEL_ROWS` + `_draw_torso`）不到 8%。原因是**四个层各自把「有且仅有一个角色，名叫 gus」编码成了结构不变式而不是数据**：`character_motion.py` 的模块级常量、`asset_lab.py` 的槽位字面量、JS 契约、JSON schema。

### 三类改动

**(i) 纯复制改名**

- `assets/<name>-rig/rig.json` —— 从 Gus 的复制
- 身份层美术：头部像素图（4 × 16-17 行 × 24 字符）+ 躯干绘制函数。**这是唯一真正的创作工作**
- 重跑 build / qa 产出物

**(ii) 需要真泛化**

| 项 | 位置 | 量级 |
|---|---|---|
| 把角色参数从模块全局收成 `Character` 记录（调色板、头部图、躯干绘制、解剖、姿态、门禁阈值、动作） | `character_motion.py` | 2-3 天 |
| QA 输出文件名与默认 rig 路径带上角色 id（`slot` / `displayName` / `jobId` / `sourceRig` 已改为从 rig 派生） | `character_motion.py` | 1-2 小时 |
| 多 sheet 打包：单例 `gus_sheet` 改成按角色循环 | `asset_lab.py` | 1-2 天 |
| 契约按角色 id 建表，`characterId` 参数贯穿校验链 | `web/asset-manifest.mjs` | 1 天 |
| `characterMotion.canonicalFrames` 增加角色维度 | `assets/manifest.schema.json` | 2-3 小时 |
| 槽位字面量派发改为按 `kind` 派发 | `asset_lab.py`、`asset_normalize.py` | 4-6 小时 |
| actor 增加角色字段，驱动动画 id 与预取 | `web/scene.mjs`、`web/pixel.mjs` | 3-4 小时 |
| pack spec、fixtures、测试更新 | 多处 | 1 天 |

**(iii) 会硬失败或静默出错的地方**

这一类最危险，动手前必须先看：

| 阻塞点 | 位置 | 失败方式 |
|---|---|---|
| `len(required) != 11` | `asset_normalize.py` 的 `_load_spec` | **硬失败**。给任一 pack spec 加第 12 个槽位，会让**所有**槽位的规范化一起挂掉 |
| `spec.get("requiredSlots") != required_slots` | `asset_lab.py` 的 `_load_runtime_spec` | **硬失败**。`CORE_SLOTS` 和 JSON spec 必须同步改，否则激活时 `runtime_spec.invalid` |
| 激活要求每个槽位都有已接受版本 | `asset_lab.py` 的激活完整性检查（`pack.incomplete`） | **激活冻结**。一声明新角色槽位，整包激活就被 `pack.incomplete` 挡住，连重新激活旧包都不行 |
| `len(sheets) != 1 or sheets[0].id != "character.gus"` | `asset_lab.py` 的 `_runtime_entries` | 第二张 sheet 直接被拒 |
| 按 `kind === 'character'` 过滤却拿单个角色的 `frameIds` 比对 | `web/asset-manifest.mjs` 的 `validateGusContract` | **最阴的一条**。新角色的帧会撑爆**旧角色**的门禁，再引发一串误导性的逐帧错误 |
| `/^animation\.gus\.…/` 正则 | `web/asset-manifest.mjs` 的 `resolveAnimationFrame` | **静默**。新角色的「未验证动作回退到中立 idle」安全网**根本不会触发**，一个没过门禁的角色会直接播放它可能损坏的走路动画，全程无任何报错 |
| `READABILITY_CONSTRAINTS` / `ACTION_CONSTRAINTS` 做全等比较 | `character_motion.py` 的 `load_rig` | 新角色必须和 Gus **同身高、同头围、同像素预算、同步幅、同节奏**，任何偏差直接 `MotionRigError` |
| `write_default_layers` 从模块全局重绘 | `character_motion.py` 的 `write_default_layers` | **静默写错**。会把 Gus 的像素写进新角色的 layers 目录，而且完全可复现——一个可复现的错误 |
| QA 文件名前缀写死 | `generate_qa_artifacts` 里的 `gus-*` 文件名 | 两个角色共用一个 `--output-dir` 会静默互相覆盖证据 |
| 调色板特权按字面槽位判定 | `asset_lab.py` 的 `_palette_warnings` | 新角色拿不到 8 个 player accent 色，每个 accent 像素都会告警 |
| `ATLAS_MAX_SIZE = 1024` | `asset_lab.py` 的 `ATLAS_MAX_SIZE` | 第 2 个角色放得下，**第 4 个临界、第 5 个失败** |

### 建议的推进顺序

先做 (iii) 里的硬阻塞（它们会在第一次尝试时就炸），再做 (ii) 的 1 和 3（工作量大头），最后才是美术。**不要先画图**——在 `load_rig` 还强制新角色与 Gus 同身高的情况下画出来的图，很可能一进门禁就被打回。

## 十一、已知缺口

诚实记录尚未解决的问题。

**1. 运行时门禁进不了 CI。** 滑步、转向重置相位这类缺陷只在播放时成立，而承担这部分逻辑的方法是 `IsometricScene` 的私有方法，测不到。要补这一层，需要把它抽成导出的纯函数，然后断言：「给定 sprite 声明的步幅和一段已知位移，相位推进量恰好等于脚部行程对应的帧数」。**这是唯一还完全靠人眼的门禁类别。**

**2. 文档与代码的一致性靠人维护。** 本项目明确决定不加自动检查。缓解手段就是本文开头那条约定：**不写当前阈值，只写键名并指向源文件**。

### 已修复

- ~~方向轴常量住在角色模块里~~ → 已移入 `codex_v0/isometric.py`，且**从投影推导而非手写**：给定每个方向的世界步进和投影公式，`FORWARD_SCREEN_X` 与 `NEAR_SIDE_SCREEN_X` 都是算出来的，模块导入时断言校验。第二个角色现在无法把它们写错。`DIRECTIONS` 的三份 Python 副本也一并收敛到这里。
- ~~`sourceRig` / `jobId` 是硬编码常量~~ → 已改为从实际编译的 rig 派生。`rig.json` 里那个一直没人读的 `character` 字段现在是权威来源，`load_rig` 会校验它，产出的 sidecar `slot` / `displayName` / `metadata` 里的 `character` 字段 也随之而来。

### 文档必须机械地为真

`character_motion.py` 的 docstring 曾经写着「每个像素都来自已审批的组件单元」。实际上那 24 个图层 PNG 与模块自己的绘制代码**逐字节一致**——根本没有任何外部审批环节。参考图 `gus-turnaround-v2.png` 代码从不读取。

这不是小事：它让审阅者以为有一道人工把关，而那道关不存在。

**往这份文档里加任何一句「我们会检查 X」之前，先确认代码里真的有那个检查。**
